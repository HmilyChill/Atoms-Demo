# 01 · 主要问题分解（WBS）：把 6–8 小时切成可交付的块

> 上游文档：`docs/00-问题解析.md`
> 本文目标：把"做一个 Atoms Demo"分解为**有优先级、有验收标准、有依赖、有估时**的模块，并用时间盒锁住范围。
> **本阶段约束**：仅分解，不编码。

---

## 1. 分解原则（发生冲突时的裁判规则）

1. **闭环优先**：宁可窄而完整，不可宽而破碎。一个能跑通的主链路 > 五个半成品。
2. **可演示优先**：每条链路都要能在评审面前 **3 分钟内跑通**。
3. **稳定优先于功能数**：预览不报错是底线，功能少一个不致命，白屏一次就致命。
4. **诚实交付**：做不完的功能明确标注"未完成"，**绝不做假按钮**。
5. **部署前置**：第 0 步就把公网空壳部署打通，不把风险留到最后。

---

## 2. 范围分层（先锁范围，再谈实现）

### 🟥 P0 — 必须做：构成"最小可验收闭环"

| 能力 | 验收标准 |
|---|---|
| 项目初始化与身份 | 可注册/登录（或等效的轻身份），可新建项目 |
| 自然语言需求输入 | 输入一段需求，系统能解析并进入生成流程 |
| 计划确认 | 生成前给出计划/契约，用户可确认或纠偏 |
| 多智能体协作生成 | **至少 3 个角色**可见，各自有状态与产出 |
| 生成可运行的应用 | 产物是能点、能填、有状态的真实网页应用 |
| 实时可视化预览 | 同界面内 iframe 实时渲染，无报错 |
| 数据持久化 | 刷新后项目 / 会话 / 产物 / 应用数据仍在 |
| 公网部署 + 源码 + 文档 | 链接可访问、仓库 public、说明文档齐全 |

### 🟨 P1 — 应做：形成"完整体验"（P0 完成后按序插入）

- **二次迭代**：对已生成应用继续提需求，产生新版本
- **版本与回滚**：每次迭代一个版本，可对比、可回滚
- **需求契约**：显式"必做 / 禁做 / 验收点"，生成后逐条核对
- **质量校验与自愈**：Verifier Agent 自动校验，失败自动修复（最多 2 轮）
- **产物导出**：下载可运行代码包 / 生成只读分享链接
- **过程可观测**：Agent 时间线含状态、耗时、错误原因

### 🟩 P2 — 加分（仅在 P0/P1 全绿且有余量时）

- 预览中**选中元素直接改**（Atoms 的招牌交互）
- 模板 / 案例库（一键填充示例需求）
- 多模型选择
- 生成应用内置图表 / 数据看板
- 生成应用的只读分享链接

### ⬛ 明确"不做"（要写进说明文档，主动管理预期）

- 真实多文件工程级仓库生成（超出时间盒，且与稳定性目标冲突）
- 为用户把生成物部署到真实云环境
- 支付、复杂 RBAC 权限体系
- 类 Figma 的可视化设计器
- 接入 Atoms 官方 API（题目明确不考察）

## 3. 模块分解（M1–M10）

> 估时按 6–8 小时总预算分配；依赖列的箭头表示"必须先有前者"。

### M1 · 身份与项目空间 ⏱ 40min · P0
- **目标**：让"谁的项目、谁的会话"成立
- **关键点**：轻量注册/登录（邮箱或一键进入）；项目列表 + 新建/重命名/删除
- **验收**：注册 → 新建项目 → 刷新后项目仍在 → 退出后数据不串
- **依赖**：M9（持久化）
- **风险**：身份体系做重了会吃掉 1 小时 → **只做最小可用**

### M2 · 需求输入与会话 ⏱ 30min · P0
- **目标**：一个能承载多轮对话的输入区
- **关键点**：自然语言输入、附件（可选）、发送/中断、消息历史、空状态引导
- **验收**：输入需求后消息入列并触发生成；生成中可中断
- **依赖**：M1

### M3 · 计划与需求契约 ⏱ 30min · P0
- **目标**：**先计划、后执行**，把"需求漂移"挡在生成之前
- **关键点**：输出结构化计划（要做什么 / 不做什么 / 验收点）；用户确认或纠偏后再执行
- **验收**：未确认不会开跑；确认后计划被后续产物逐条对应
- **依赖**：M2、M4
- **风险**：这是最容易省掉、但最能体现工程思维的一环 → **不建议省**

### M4 · 多智能体编排引擎 ⏱ 90min · P0 ★核心
- **目标**：真正的多角色协作，而非"套一层循环的 LLM 调用"
- **关键点**：状态机（计划 → 执行 → 校验 → 收敛）；每个 Agent 的**输入输出契约（schema）**；上下文裁剪；失败重试与超时；事件流对外广播
- **验收**：至少 3 个角色依次产出结构化产物；任一步失败可重试且状态正确
- **依赖**：M3
- **风险**：上下文爆炸、产物格式漂移 → 用 schema 强约束

### M5 · 应用规格（App Spec）与渲染运行时 ⏱ 120min · P0 ★★技术心脏
- **目标**：把"应用"变成**可生成、可校验、可增量修改**的结构化规格，并确定性渲染成真应用
- **关键点**：Spec 覆盖 页面 / 布局 / 组件 / 数据模型 / 动作 / 校验规则 / 主题令牌；渲染器把 Spec 变为可交互 React 应用；Spec 与运行时共用同一份类型定义
- **验收**：同一份 Spec 两次渲染结果一致；生成的表单能提交、列表能新增、数据能落库
- **依赖**：M4
- **风险**：**这是全项目最大的单点风险**。若走"自由生成整个工程"路线，M6/M7/M8 的风险成倍放大 → **强烈建议走规格驱动路线**
- **取舍**：表达力 vs 稳定性。先覆盖「表单 + 列表 + 详情 + 看板」四类典型页面即可支撑大量需求

### M6 · 实时预览沙箱与运行时错误回传 ⏱ 60min · P0
- **目标**：生成物在宿主内实时渲染，且**它的报错能被我们看见**
- **关键点**：iframe `sandbox`；`srcdoc`/blob URL 装载；`postMessage` 双向通道（宿主 → 预览注入数据，预览 → 宿主上报错误/事件）；加载态与错误浮层
- **验收**：预览可交互；人为注入错误时，宿主能显示明确错误而非静默白屏
- **依赖**：M5
- **风险**：CSP / 跨域限制 → **提前 15 分钟做技术验证**

### M7 · 迭代修改与版本管理 ⏱ 60min · P1 ★延展能力首选
- **目标**：对已生成应用继续提需求，改对地方、不破坏原有功能
- **关键点**：需求 → 定位 Spec 片段 → 增量 patch；版本快照；Diff 视图；一键回滚
- **验收**：第二轮的修改只影响目标片段；回滚后回到上一版且数据不丢
- **依赖**：M5、M6、M9
- **风险**：改坏原功能 → 版本快照是安全绳，**必须先有版本再允许改**

### M8 · 质量校验（Verifier/QA）与自愈 ⏱ 60min · P1 ★差异化亮点
- **目标**：**杜绝"报错却宣称完成"**——这是 Atoms 被公开吐槽最多的点
- **关键点**：Spec 结构校验 → 渲染冒烟 → 交互冒烟（按契约逐条核对：必做项存在、禁做项不存在）；失败自动修复（上限 2 轮）；最终如实上报"通过 / 部分通过 / 失败 + 原因"
- **验收**：故意构造一个不满足契约的 Spec，系统能检出并修复或如实报错
- **依赖**：M3、M5、M6
- **风险**：修复循环耗时 → 设硬上限，超限即降级并如实上报

### M9 · 持久化与状态恢复 ⏱ 60min · P0
- **目标**：长任务不丢、刷新不丢、生成物数据不丢
- **关键点**：五类实体 —— 项目 / 会话 / 消息 / 产物（含 Spec 与版本）/ 生成应用的数据；生成中的 run 状态可恢复；统一持久层（宿主与生成物共用）
- **验收**：生成进行中刷新页面，回来后状态与产物正确；生成应用内新增的数据刷新后仍在
- **依赖**：无（但被几乎所有模块依赖 → **优先做**）
- **风险**：生成物数据与宿主数据两套存储 → 一开始就统一

### M10 · 交付：部署 + 文档 + 演示兜底 ⏱ 70min · P0
- **目标**：让评审"点得开、跑得动、看得懂"
- **关键点**：
  - 公网部署（**第 0 步就打通空壳**，最后只做复测）
  - GitHub public 仓库 + README（环境要求、启动命令、演示路径、无 key 时的降级说明）
  - 说明文档：实现思路与关键取舍 / 完成度（做了 & 没做）/ 后续扩展与优先级
  - **演示兜底**：无 API key 时的 Mock/回放模式，预置 1–2 个示例需求，随时可演示
  - 2 分钟录屏或 GIF（防止评审网络/额度异常时无法体验）
- **验收**：陌生人拿到链接能在 5 分钟内完成一次完整主流程
- **依赖**：M1–M9
- **风险**：**这是最容易在最后 1 小时翻车的一环** → 前置

## 4. 关键路径与依赖

```
P0 关键路径：
M9(持久化) → M1(项目) → M2(输入) → M3(计划) → M4(编排) → M5(Spec+渲染) → M6(预览) → M10(交付)
                                                            │
P1 支线（挂在 M6 之后）：─────────────────────────────────────┤
                                                            ├→ M7(迭代+版本)
                                                            └→ M8(校验+自愈)

贯穿全程：部署空壳提前打通（T+0 完成）、Mock 兜底模式（T+0 预留接口）
```

**读法**：M5 是所有支线的共同前置。**M5 一旦延期，P1 全部顺延** → 因此 P1 的功能必须在 M5 稳定的前提下才允许启动。

## 8. 复核补充（第二轮）：分解修正与新增风险

### 8.1 修正 1（最重要）：估时与排期不自洽，必须分档

**问题**：§3 的 M1–M10 估时合计 **620 分钟（约 10.3h）**，而 §5 排期给模块的可用时间只有 **420 分钟**（480 减 60 buffer）。这不是估算偏保守，而是**按原排期执行必然超时**。

**修正后的分档方案**（单模块修正估时见 `04-模块实现细则与验收标准.md` §2）

| 档位 | 包含模块 | 合计 | 满足"至少一个延展能力" | 差异化亮点 | 状态 |
|---|---|---|---|---|---|
| 保底 | M0–M6 + M9 + M10 + M11 + M12 | 约 **485 min（8.1h）** | ❌ **不满足** | ❌ 无 | 已排除（不合规） |
| 推荐（8h 档） | 保底 + **M7**（迭代+版本） | 约 **520 min（8.7h）** | ✅ 满足 | ⚠️ 弱（无校验自愈） | 备选 |
| **✅ 完整（9–10h 档）** | 推荐 + **M8**（校验自愈） + **M13**（导出） | 约 **580 min（9.7h）** | ✅✅ | ✅ 强（正面对冲 Atoms 短板） | **已选定（第三轮决策）** |

> ⚠️ **合计数字已于第四轮复核修正**：原 440 / 475 / 535 min 系**漏算 M0、M11、M12** 的算术错误，正确值为 **485 / 520 / 580 min**。
> 且上表为**纯开发工作量**；计入每阶段集成与 DoD 验收开销（约 10%）后，完整档实际约 **665 min ≈ 11.1h**（见 `03` §9 阶段合计）→ **"9–10h" 属乐观估计**，时间不足时按降档预案处理。

**结论**
1. **"保底"档不满足题目要求**——题目明确写了"尽量覆盖…至少一个延展或衍生能力"，所以它不是可选项。
2. ✅ **已决策：采用完整档（9–10h）** → **实施范围 ＝ M0–M13 全量**，M8 与 M13 进入实施范围。
3. **降档预案保留**：若实际时间不足，按 **① 先砍 M8 → ② 再砍 M13** 的顺序降档（顺序不可颠倒：M8 的差异化价值高于 M13）。该预案应写入说明文档——它本身就是"复杂度控制与取舍"的展示点。
4. **M11（安全配额）与 M12（可观测留痕）在任何档位都不能砍**——前者防止你自己的额度被烧光，后者是"可交付性"分数的直接来源。
