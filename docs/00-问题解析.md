## 1. 任务还原：一句话说清

原文核心句：

> 实现一个**可运行的网页应用**，具备类似 Atoms 的能力与 UI 交互体验，即**通过智能体驱动的方式完成代码（应用）生成**，并将**生成的应用以可视化网页形式进行展示**。

翻译成一句工程命题：

> 用户用自然语言描述一个应用 → 多个智能体协作把它"设计并实现"出来 → 产物是一个**真的能点、能填、能存**的网页应用，并在同一界面里**实时预览** → 全过程可持久化、可迭代、可交付。

由此得到三条**不可让渡的支柱**（砍任何一条，题目就没做）：

| # | 支柱 | 含义 | 反例（做了也不给分） |
|---|---|---|---|
| P-1 | **Agent 驱动** | 生成过程由多个角色化的智能体协作完成，且过程**可见** | 一个输入框套一次 LLM 调用，无角色无过程 |
| P-2 | **真应用产物** | 生成物是能交互、有状态、数据不丢的应用 | 生成一份 PRD / 一张截图 / 一段只读代码 |
| P-3 | **可视化展示** | 生成物在同一界面内实时预览并可操作 | 只给下载链接 / 只能看代码不能点 |

## 3. 逐条需求解析（原文 → 真实意图 → 可验收标准）

| 原文要求 | 真实意图 | 可验收标准（评审会这么测） | 常见踩坑 |
|---|---|---|---|
| 具备**真实交互**（而非纯静态展示） | 有状态、有事件、有反馈的完整链路 | 能完成一次端到端操作，并观察到明确的状态变化 | 假按钮、假进度条、点了没反应、"演示模式" |
| 具备**数据持久化**（不限技术方案） | 刷新/重开/换设备后数据仍在 | 刷新页面后项目、会话、产物仍在；生成出来的应用里的数据也在 | 只存内存；localStorage 但刷新即丢；持久化写了却没接线 |
| **基本使用流程**（如初始化 / 注册 / 核心主流程） | 原文明确点名"注册" → 需要身份与项目初始化 | 可注册/登录 → 可新建项目 → 进入核心生成主流程 | 跳过身份体系，导致"项目/会话归属"讲不清，多轮迭代无处挂载 |
| 至少一个**延展或衍生能力** | 考察产品思维，不是一个孤立 demo | 至少一条完整、可演示、可复述的延展链路 | 罗列 5 个半成品，等于 0 个 |
| **实际可用的功能**，而不仅是概念验证（PoC） | 评委会**真的去点** | 主流程无 JS 报错、无死链、无"待开发"占位页 | 预览 iframe 白屏/报错，却宣称"开发已完成" |
| 6–8 小时专注开发，**48 小时内提交** | 时间盒是硬约束 | 必须为部署 + 文档预留时间 | 8 小时全花在功能上，最后 1 小时无法部署 → 直接判不合格 |
| **不考察是否"用 Atoms 做 Atoms"** | 别把时间投在接入 Atoms 上 | 独立实现即为正解 | 花半天申请额度、对接未公开 API，属于纯浪费 |

## 4. 参考产品 Atoms 拆解（我们要对标的体验基线）

**产品定位**：Atoms（原 MGX，DeepWisdom / MetaGPT 团队）是 AI 多智能体全栈产品开发平台（[atoms.dev](https://atoms.dev/)、[帮助中心](https://help.atoms.dev/en)）。

**角色分工**（公开资料）：

| 角色 | 代号 | 职责 |
|---|---|---|
| 团队领导 | Mike | 统筹全局、协调各 Agent |
| 产品经理 | Emma | 需求分析 → PRD |
| 架构师 | Bob | 技术方案 → 架构图 / 数据库 / 接口设计 |
| 工程师 | Alex | 按设计生成代码 |
| 数据分析师 | David | 数据分析、优化决策 |

**主管线**：`描述产品 → 查看计划（蓝图）→ Agent 构建 → 预览迭代 → 发布/导出`

**界面要素拆解**（这些就是我们 UI 的对齐清单）：

1. **需求输入区**：自然语言输入 + 附件上传 + 模型选择 + 官方案例模板
2. **计划确认区**：先出蓝图，**用户确认后**再执行（不是黑箱直接开跑）
3. **Agent 时间线**：角色卡、当前动作、状态、耗时
4. **产物区**：PRD / 架构设计 / 数据库设计 / 接口设计 / 时序图，分 Tab 或分步呈现
5. **代码 / 文件树**：可查看、可导出
6. **实时预览**：iframe 渲染，可选中界面元素继续修改
7. **分享与导出**：Share → Export（下载完整工程 ZIP）；支持导入本地项目继续迭代
8. **项目 / 历史列表**：回合制多轮对话，支持持续迭代

**体验精髓（比功能更重要）**：**过程可见**（不是等 30 分钟黑箱）、**先计划后执行**、**可干预**（中途纠偏）、**产物可带走**（导出）。

## 5. 差异化机会：从 Atoms 的已知短板反推（= 创新性得分点）

公开评测（如[掘金 MGX 体验实录](https://juejin.cn/post/7479431076207018036)、[腾讯云 Atoms 实践](https://cloud.tencent.com.cn/developer/article/2716319)）暴露了以下短板。**每一条都是我们的机会**：

| Atoms/MGX 已知短板 | 我们的做法 | 命中的评估维度 |
|---|---|---|
| 多智能体各干各的，Leader 只收状态不验质量 | 引入 **Verifier/QA Agent**，产物必须过校验才算完成 | 工程思维 / 创新性 |
| 无测试角色，预览报错却宣称"已完成" | 生成后**自动冒烟测试**（结构校验 + 渲染 + 交互断言），失败自动修复，如实上报 | 完成度 / 用户体验 |
| 需求漂移（输入明确需求却被擅自改动） | 显式**需求契约**（必做 / 禁做 / 验收点），生成前锁定、生成后逐条核对 | 工程思维 |
| 只有前端 mock，没有真实后端与持久化 | 生成的应用**自带真实持久化**，数据不丢 | 完成度 |
| UI 无亮点 | 内置设计系统 / 主题令牌，产物默认有设计感 | 用户体验 |
| 预览反复报错、找不到模块 | **受限生成**（结构化规格 + 确定性渲染），稳定性提升一个数量级 | 完成度 / 工程思维 |
| Token 消耗快、耗时不可控 | 分级模型 + 缓存 + 超时 + **无 key 也能演示的 Mock 模式** | 工程思维 |

> **结论**：我们的"创新性"不来自更多功能，而来自 **"生成即可用 + 生成物可验证 + 过程可干预"** 这条与 Atoms 形成差异的质量主线。

## 6. 技术难点剖析（D1–D8）

| 编号 | 难点 | 本质矛盾 | 应对方向 | 主要风险 |
|---|---|---|---|---|
| **D1** | 让 LLM 稳定产出"能跑"的应用 | 自由生成整个工程 = 不可控、不可验证 | **结构化 App Spec**（页面/组件/数据模型/动作）+ 确定性渲染器；JSON Schema 约束 + 失败重试 | 规格表达力不足，需覆盖常见组件 |
| **D2** | 实时预览与沙箱 | 要在宿主页面里安全地跑生成物，并**捕获它的运行时错误** | iframe `sandbox` + `srcdoc`/blob URL + `postMessage` 双向通道 | 错误捕获缺失 → 重蹈"白屏还宣称完成" |
| **D3** | 流式体验与事件协议 | 用户要看到"正在发生什么" | SSE（优先，简单可靠）或 WebSocket；定义事件协议：`agent.started / agent.delta / artifact.created / preview.updated / run.failed`；断线重连 + 幂等 | 事件设计混乱 → UI 状态机难写 |
| **D4** | 多智能体编排 | "多智能体"很容易退化成"多次串行调用" | 状态机 / 计划-执行-校验三段式；每个 Agent 的**输入输出都有 schema**（产物契约）；控制上下文长度 | 上下文爆炸、产物对不上 |
| **D5** | 持久化与并发 | 生成是长任务，中途刷新/关闭怎么办 | 项目 / 会话 / 消息 / 产物 / 版本 五类实体；生成状态可恢复；多标签页冲突处理 | 长任务中断即丢，体验崩坏 |
| **D6** | 迭代修改（二次开发） | 对已生成应用继续提需求，改哪里？ | 需求 → 定位 App Spec 的对应片段 → 增量 patch → 版本化 → 可回滚。**这是"至少一个延展能力"的最佳候选** | 上下文丢失导致改坏原功能 |
| **D7** | 成本 / 延迟 / 可用性 | 演示不能赌网络和额度 | 分级模型 + 结果缓存 + 超时取消 + **无 API key 的 Mock/回放模式**（保证任何时候都能演示） | 演示当场挂掉 = 全盘皆输 |
| **D8** | 部署与交付 | 本机环境限制 | 已实测：`node v24.15.0` / `npm 11.12.1` / `pnpm 11.24.0` / `python 3.11.7` / `git 2.54.0` 可用；**`docker`、`vercel` CLI 不可用** → 需选择 Git 直连型托管平台并预留时间 | 部署踩坑吃掉最后的 buffer |

## 7. 隐藏考点与红线

1. **在线链接必须真公网可访问**。`localhost` / 局域网 IP / 需要本地起服务的链接，等于没交。
2. **GitHub 仓库必须 public**，且 README 能让评审在 5 分钟内跑起来。
3. **笔试文档标题要标注名字，分享范围要"互联网获得链接的人"**（图片附件专门强调了这一点）。
4. **48 小时窗口 ≠ 8 小时工作量**：必须把部署与文档塞进时间盒，而不是"功能做完再说"。
5. **题目要求保密**，不得对外传播共享。
6. **"不考察用 Atoms 做 Atoms"**：时间应全部投在产品与工程本身。
7. **评审会真机点击**：主流程任何一处报错，都会同时扣"完成度"和"用户体验"两项分。
8. **文档会有专人评估，且注意文档评论**：坦诚写明"哪些没做、为什么没做、下一步优先级"，比堆砌吹嘘更契合"可交付性"维度。
9. **确认任务起算时间**：48 小时从何时开始计，直接决定排期是否需要压缩。

## 8. 评分策略：我们的分数从哪里来

题目给了 5 个评估维度。把它们翻译成"评审实际会做什么"，才知道力气该往哪使：

| 评估维度 | 评审实际在看什么 | 我们的对应动作 | 自检问题 |
|---|---|---|---|
| **完成度** | 功能完整性、稳定性、基本工程质量 | P0 全绿；主流程零报错；TS 类型与运行时校验双保险；失败路径有兜底 | 一个陌生人从零走一遍主流程，会在哪里卡住？ |
| **工程思维** | 任务分解、技术选型、复杂度控制与取舍 | 三层适配器；可回退的 A/B 方案；P0/P1/P2 分层；**明确的"不做"清单** | 如果时间被砍掉一半，我先砍哪一块？为什么是它？ |
| **用户体验** | 交互是否清晰、流程是否顺畅、是否"可用" | 三栏布局对齐 Atoms；过程可见；状态/进度明确；失败有解释；空状态有引导 | 第一次打开的人，知道下一步该点哪里吗？ |
| **创新性** | 是否有亮点设计、独特视角、可扩展潜力 | 质量校验自愈 + 需求契约 + 版本回滚（**正面对冲 Atoms 的公开短板**） | 我们比 Atoms 好在哪？能用一句话说清吗？ |
| **可交付性** | 文档清晰度、可运行程度、整体完成质量 | 在线链接 + public 仓库 + README + 说明文档（**含"没做什么"**）+ 录屏 | 评审能在 5 分钟内把它跑起来吗？ |

**分数优先级判断（这一条决定了排期）**：

1. **门槛项 = 完成度 + 可交付性** → 不达标直接出局，再多亮点也无效。
2. **区分项 = 工程思维 + 用户体验** → 大多数候选人都能"跑通"，差距全在这里。
3. **拔高项 = 创新性** → 只有在前两项稳住时，亮点才值钱。

> 所以资源分配顺序是：**可运行 → 可交付 → 好用 → 有想法**。
> 反过来做（先追亮点、最后才想部署和文档）是这类限时笔试**最常见的失败模式**。
>
> 另外记住：在说明文档里如实写清"**哪些没做、为什么没做**"，在"可交付性"上是**加分**而不是减分——评审要看的是你的判断力，不是完美。

### 9.0 选型尺子：先定评价标准，再谈好坏

脱离约束谈技术栈是空话。本项目的真实约束如下，权重从高到低：

| 权重 | 约束 | 含义 |
|---|---|---|
| ★★★★★ | **6–8h 时间盒** | 任何方案，只要"搭起来"超过 1 小时就要扣分 |
| ★★★★★ | **必须公网可访问** | 部署链路必须短且一次成功，不能有"最后一步卡住"的风险 |
| ★★★★★ | **必须真持久化** | 且**跨设备可验证**更佳（评审可能换浏览器） |
| ★★★★☆ | **无 LLM Key**（你当前状态） | 系统必须**无 key 也能完整演示** |
| ★★★★☆ | **无云平台账号**（你当前状态） | 优先"邮箱注册即可、免信用卡、免实名"的平台 |
| ★★★★☆ | **主流程零报错** | 稳定性 > 功能数（评估维度里的"完成度/用户体验"） |
| ★★★☆☆ | **体现工程思维** | 评审想看结构、抽象与取舍，不只是"能跑" |
| ★★☆☆☆ | **本机无 docker / vercel CLI** | 已实测，见 §10；不能用 CLI 一键部署的路径要谨慎 |

> **由这把尺子直接推出的三条结论**：
> 1. **"无 key 也要能演示"不是降级方案，而是 P0 需求**（你当前就没有 key）。
> 2. **部署平台的选择会反向决定持久化方案**，两者必须一起定，不能分开选。
> 3. **凡是可以后置的决策，都应该用适配器隔离掉**（见 §9.10），把不确定性变成配置项。

### 9.1 架构形态（第一个必须定的决策）

| 方案 | 形态 | 优点 | 缺点 | 部署难度 | 时间成本 | 建议度 |
|---|---|---|---|---|---|---|
| **A** | **纯前端 SPA**（React）+ 浏览器持久化（IndexedDB）+ 浏览器直连 LLM | 最快；零服务端；零冷启动；静态托管随便放；无密钥泄露风险（用户自带 key，即 **BYOK**）；调试最简单 | 数据只在本浏览器，换设备即"丢失"；LLM 调用受 **CORS 限制**；"服务端工程"含量低，工程思维得分偏弱 | ★（最低） | 最低 | ⭐⭐⭐ |
| **B** | **单仓全栈**（Next.js App Router：UI + Route Handlers 同仓）+ 托管数据库 + 服务端调用 LLM | 工程完整度与稳定性平衡最好；密钥在服务端；跨设备持久化；编排/日志/校验都好做；部署平台零配置支持 | Serverless 平台**文件系统只读**（不能用本地 SQLite 文件）；**函数有执行时长上限**（长任务需拆步或用流式）；本地与线上有差异 | ★★ | 中 | ⭐⭐⭐⭐⭐ |
| **C** | **前后端分离**（Vite 前端 + 独立 Node 服务 + SQLite 文件） | 最接近真实生产工程；可长连接/WebSocket；SQLite 单文件持久化最省心；无函数超时问题 | 需要**容器型平台**（且大多要信用卡或会睡眠）；本机**无 docker**；部署链路最长，最容易在最后 1 小时翻车 | ★★★★（最高） | 最高 | ⭐⭐ |
| **D** | **纯前端 + BaaS**（前端直连 Supabase/Neon） | 无需自建后端即可拿到 Postgres 持久化；跨设备可验证；静态托管 | 业务逻辑仍在浏览器；多引入一个账号与 SDK | ★★ | 中低 | ⭐⭐⭐⭐ |

**关键洞察（B 方案的主要风险与解法）**：
Serverless 平台的"函数执行时长上限"是 B 的最大暗礁——一次完整生成可能要 30–120 秒。**解法：把长任务拆成"由前端驱动的短步骤流"**（每个 Agent 一步、每步一次短请求，前端串起来 + SSE 流式推送）。这样：
- 每次请求都在平台超时以内 → **任何平台都能跑**；
- 进度天然可观测（正好是 Atoms 的体验精髓）；
- 中断/重试粒度更细，长任务刷新可恢复（呼应 M9）。

> 这个"拆步"设计让 **B 的风险从"高"降到"中"**，也是我推荐 B 而不是 C 的主要原因。

### 9.4 生成策略（本项目**最大**的技术决策）

| 维度 | **① 结构化 Spec + 确定性渲染** | **② 自由代码生成**（LLM 写 React → 沙箱构建运行） | **③ 混合：Spec 为主 + 导出源码** |
|---|---|---|---|
| 稳定性 | ★★★★★（同一 Spec 渲染结果确定） | ★★（易白屏/缺依赖/模块找不到） | ★★★★ |
| 产出速度 | 秒级 | 数十秒～数分钟 | 秒级（导出为异步） |
| 可校验性 | ★★★★★（Spec 是结构化数据，可逐条断言） | ★（只能跑起来看，难自动断言） | ★★★★ |
| 可增量修改 | ★★★★★（定位 Spec 片段改） | ★★（改坏原功能概率高） | ★★★★ |
| 表达力上限 | ★★★（先覆盖 表单/列表/详情/看板） | ★★★★★（理论上无上限） | ★★★★ |
| 实现工作量 | 中（要自己写渲染器） | 高（要沙箱 + 构建 + 依赖 + 错误回传） | 中高 |
| 6–8h 内翻车风险 | **低** | **高** | 中 |
| 对"生成代码"的字面贴合 | 中（生成的是规格，代码是渲染产物） | 高 | **高**（可导出真实源码） |
| 评分倾向 | 工程思维 / 完成度 / 稳定性占优 | 创新性占优，但"完成度"风险极高 | 折中 |

**分析结论**：
- 题目原文是"完成**代码（应用）生成**"，但括号里的"**应用**"才是重心，且"生成的应用以**可视化网页形式**展示"才是硬指标。
- ② 的致命问题不是"难写"，而是**它把 M6（预览）和 M8（校验自愈）的风险同时放大**——而这两块正是我们用来对冲 Atoms 短板的差异化模块。**为了"更像"而牺牲"可控"，性价比不划算。**
- ③ 是最优解：主管线走 ① 保证 6–8h 内稳，再用"**导出为真实可运行源码**"作为延展能力，同时满足"真的生成了代码"的说服力，还能把 ① 的表达力上限问题绕过（导出的代码用户可以自己改）。

> **我的建议：③（Spec 驱动为主 + 导出真实源码作为延展能力）。** 若你更看重"生成过程的震撼感"且愿意承担风险，可选 ②，但我会把 P1/P2 全部砍掉来保它。

| 是否做"选中元素直接改"（P2） | 可后置 | 有余量才做 |

**把不确定性关进适配器**——这是我对本项目最重要的一条工程建议：

```
LLM 适配器：MockProvider | FreeTierProvider(Cerebras/Groq/SambaNova) | ByokProvider | ServerKeyProvider
存储适配器：IndexedDBStore | D1Store | TursoStore | SupabaseStore
预览适配器：IframeSpecRenderer | (P2) WebContainerRunner
```

有了这三层适配器，**"有没有 key""用哪个平台""要不要换存储"都变成改一行配置**，而不是重写项目。这正是 6–8h 时间盒下最值得投入的抽象。

## 11. 复核补充（第二轮）：新增注意点

> §1–§10 是首轮分析。以下是把方案锁定为 **「方案 B + 生成策略 ③ + 自备 DeepSeek key + 公网 Vercel + public 仓库」** 之后**才暴露出来的风险点**——首轮没有它们，是因为首轮还没定方案。

### 11.1 安全与密钥（最高优先级，全部由"公开仓库 + 自备 key"推导而来）

| 编号 | 注意点 | 为什么现在才暴露 | 必须做的事 |
|---|---|---|---|
| **A1** | **公开仓库 × 自备 key ＝ 头号风险** | 首轮还没定"仓库公开 + 服务端持 key" | `.gitignore` 必须先于任何密钥写入；key 只放平台环境变量；开启 Secret Scanning；**一旦泄露立即轮换**；README 与截图不得出现 key |
| **A2** | **公网 demo × 服务端 key ＝ 额度会被陌生人消耗** | 方案 B 的必然结果 | 限流（IP+会话）+ 单 Run 调用预算 + **每日全局熔断**（超出自动切 Mock 并显式标注） |
| **A3** | **提示注入**：用户需求文本会进入 LLM 上下文 | 我们是"把用户输入直接喂给 Agent"的形态 | 系统约束与用户输入隔离；生成物不得因注入获得额外权限；对异常指令保持可解释 |
| **A4** | **预览沙箱越权 / XSS** | 预览承载的是"生成出来的代码" | **不可同时放开 `allow-scripts` 与 `allow-same-origin`**；生成内容中的用户数据须转义 |
| **A5** | **分享链接越权与枚举** | 方案 B 有分享能力 | 随机 token、只读、不可枚举、可失效、防 IDOR |
| **A6** | 密码与登录信息泄露 | 要做"注册"环节 | 只存哈希；登录失败**不区分**"用户不存在/密码错" |

### 11.2 Provider（DeepSeek）专项

| 编号 | 注意点 | 说明 |
|---|---|---|
| **B1** | **开工前必须验证的 6 件事** | 连通性、Base URL、模型名、**结构化输出（JSON）稳定性**、上下文长度与并发/RPM 限制、超时行为。**其中"结构化输出稳定性"最关键**——我们的编排完全建立在契约化产出之上，若它不稳，架构假设会当场落空 |
| **B2** | **单一 provider ＝ 单点故障** | 额度耗尽、限流、网络波动都会让演示挂掉 → **Mock 提供方是必然设计，不是备选**；适配器必须做到上层无 provider 分支 |
| **B3** | 用量要记账 | 记录 token 与耗时，进入 Run 与日志，作为预算熔断的依据 + 说明文档的成本证据 |
| **B4** | 中文优势 | DeepSeek 中文理解与生成强，与本项目"中文需求 → 中文界面"高度契合 → **这是一个可以写进说明文档的选型理由** |

### 11.3 部署与网络（方案 B 特有）

| 编号 | 注意点 | 说明 |
|---|---|---|
| **C1** | **国内访问 Vercel 可能不稳定** | 评审若打不开，一切归零 → **必须准备备用入口**（备用静态部署）**+ 录屏兜底**。这条首轮完全没考虑到 |
| **C2** | Serverless 函数时长上限 | "拆步"设计必须落实到**接口粒度**（每请求一步），否则一次 30–120 秒的生成会被平台打断 |
| **C3** | 只读文件系统 | 不能用本地 SQLite 文件，托管 DB **必须真的配好并验证**（不能只在本地通过） |
| **C4** | 环境变量作用域 | Preview 与 Production 都要配，否则 preview 部署会直接 500 |

### 11.4 数据与兼容

| 编号 | 注意点 | 说明 |
|---|---|---|
| **D1** | **"持久化"有两层含义** | ① 宿主侧（项目/会话/产物）② **生成的应用内部的数据**。两者都要真持久化，且要**在 UI 上看得见**（如"已保存 12:03"），否则评审无法确认 |
| **D2** | `schemaVersion` 与旧数据兼容 | 评审可能打开你早期的项目 → 必须兼容读取或**明确提示**，不允许白屏 |
| **D3** | 迭代加字段的旧数据 | 第二轮给数据模型加字段后，旧记录的默认值策略要预先定义 |

### 11.5 体验与评审视角

| 编号 | 注意点 | 说明 |
|---|---|---|
| **E1** | **"5 分钟零思考路径"** | 落地页 → 一键试用示例 → 立刻看到生成过程。**降低评审的启动成本本身就是分数** |

## 12. 一句话结论

> 这不是"做一个 AI 生成代码的玩具"，而是 **"用 6–8 小时交付一个能被陌生人独立验证的、智能体驱动的应用生成产品"**。
