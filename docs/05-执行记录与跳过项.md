## 3. 实施中发现并修复的缺陷（工程质量证据）

这些都是**测试真实抓到的问题**，不是"写完就跑"：

| # | 缺陷 | 严重度 | 如何发现 | 修复 |
|---|---|---|---|---|
| 1 | **越权访问（IDOR）**：14 处路由把 `getProjectForOwner()` 当作检查调用，但**忽略了 null 返回值**，导致 B 用户可读、甚至**删除** A 用户的项目 | 🔴 **高（安全）** | 端到端跨用户用例 | 新增 `requireProjectForOwner()`（非归属抛 `NOT_FOUND`，不泄露存在性），全量替换，并加**回归测试锁死** |
| 2 | **渲染表格直接抛错**：`el()` 的第三个参数只接受数组，而 `renderTable` 传了单个节点 → `(children || []).forEach is not a function` → **所有带行内操作按钮的表格都渲染失败** | 🔴 **高（功能性）** | jsdom 浏览器级测试 | `el()` 容错：单个节点/字符串自动包装为数组 |
| 3 | **成功提示被吞掉**：表单提交成功后的"已保存"提示，在列表刷新（整页重绘）时被销毁，用户看不到反馈 | 🟠 中（体验） | jsdom 浏览器级测试 | 引入跨 `paint()` 存活的 `flash` 反馈条 |
| 4 | **组件 id 跨页面重复**：模板中多页面复用同名组件 id | 🟠 中 | 渲染冒烟检查 | 组装 Spec 时按页面前缀规范化 id |
| 5 | **错误语义不一致**：已认证但无权访问时返回 401（未认证），与其它接口的 404 语义冲突 | 🟡 低 | 端到端用例 | 统一为 404，仅"无身份"时才 401 |
| 6 | **文档算术错误**：档位合计漏算 M0/M11/M12，620 分钟估时与排期自相矛盾 | 🟡 低（文档） | 交叉校验 | 修正为 485/520/580 分钟，并显式标注"9–10h 属乐观估计" |

> 说明：第 2 条恰是"HTTP 冒烟测不出来"的典型——接口全部返回 200，但页面其实渲染不出来。
> 这也是我坚持补上浏览器级（jsdom）测试的原因。

## 4. 环境限制与应对（本机沙箱）

| 限制 | 现象 | 应对 |
|---|---|---|
| **子进程管道 stdio 被禁止** | `spawn EPERM`：Node 测试运行器、Next 内置 TS 检查、Next 构建 worker、Playwright 浏览器下载器全部失败 | ① 测试改用 `--test-isolation=none`；② Next 跳过内置 TS 检查，改用独立 `tsc`；③ 构建启用 `experimental.workerThreads` + `cpus:1` |
| **`next dev` 无法启动** | Next 开发 CLI 在 `next-dev.js:303` **无条件 `fork()` 子进程**来启动服务器，沙箱下必然 `EPERM`（加 `--webpack` 同样失败） | 本地验证改用 **`pnpm build && pnpm start`**（已验证可用）。⚠️ **这是沙箱限制，不是代码问题**——在正常机器与 Vercel 上 `pnpm dev` 可正常工作 |
| **esbuild 的 JS API 不可用** | `transformSync` 直接报 `EPERM` —— esbuild 必须通过**管道**与自己的服务子进程通信 | 测试中的 JSX 转换改用 **TypeScript 编译器 API**（`ts.transpileModule`）：纯 JS、完全进程内，且 typescript 本就是 devDependency，**无需引入新依赖** |
| **浏览器二进制无法下载** | `playwright install chromium` 失败（下载器 fork 子进程） | 改用 **jsdom** 直接加载并测试 `public/app-runtime.js`，拿到"可交互"的可执行证据；浏览器级 E2E 列为待办 |
| **PowerShell / curl 的 TLS 不通** | `Invoke-WebRequest`、`curl.exe` 全部失败 | 网络操作一律走 Node/pnpm（已实测 `pnpm view`、tarball 下载、`api.github.com` 均正常） |
| **`git` 走 HTTPS 完全不可用** | 四种配置全部失败，真实错误为 `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`（TLS 凭据句柄无法创建）；`--webpack`、`sslBackend=schannel`、显式 CA 均无效 | ✅ **已解决**：实现 `scripts/push-to-github.mjs`，走 **GitHub REST API（Git Data API）** 重建全部提交与 tag。本地演练已验证（8 提交 / 79 blob / 420 tree 条目），拿到令牌后一条命令即可推送 |
| **WMI/CIM 命令被屏蔽** | `Get-PSDrive` / `Get-Volume` 返回 0 或拒绝访问 | 用 .NET `DriveInfo` 读取真实容量（E 盘 356 GB 空闲，C 盘 25.7 GB） |
| **C 盘空间紧张** | 你明确要求下载落 E 盘 | `.npmrc` 重定向 `store-dir` 与 `cache` 到工作区内；浏览器目录也指向 E 盘 |

### 7.1 ⚠️ 关于"线上持久化"的重要说明（本轮复核后更新）

**问题**：Vercel 的文件系统是只读的，因此线上**不能**使用当前的本地 SQLite 文件适配器。

**根因**：`StoreProvider` 目前是**同步接口**（基于 `node:sqlite` 的同步 API），
而任何远程数据库（Turso / Supabase / Neon）都必须通过 HTTP 访问 → **只能是异步**。
所以要接托管库，必须先把存储层改成 `async`，并让全部调用点 `await`
（约 20 个文件、百余处调用；编排器、事件总线、全部 API 路由都受影响）。

**本轮我做了什么**：我已经拿到并核对了 [Turso SQL over HTTP 官方协议](https://docs.turso.tech/sdk/http/reference)
（`POST /v2/pipeline`、`Authorization: Bearer`、`{type,value}` 单元格编码、需显式 `close` 以免连接泄漏），
确认**可以零依赖（纯 `fetch`）实现**。

**本轮我为什么没做**：这是一次**跨全仓的破坏性重构**，而当前交付物处于"全绿且已验证"的状态
（35 单测 + 70 端到端 + 21 部署自检），且重构后**无法在本环境对着真实 Turso 验证**（没有凭据）。
在无法端到端验证的前提下动这种规模的重构，风险大于收益——这个判断本身也是"复杂度控制"的一部分。

**两条可选路径**（拿到账号后按此执行）：

| 路径 | 需要改代码？ | 说明 |
|---|---|---|
| **A. 换部署形态（最快）** | ❌ **零改动** | 部署到带持久卷的容器平台（Railway / Fly / VPS / Oracle Always Free）。SQLite 文件照常工作，**当前代码直接可用**。代价：需信用卡或注册成本，且部分平台免费档会睡眠 |
| **B. 留在 Vercel + 异步存储改造** | ✅ 需重构 | 先把 `StoreProvider` 全部方法改为返回 Promise、调用点补 `await`，再实现 `TursoStore`（纯 fetch）。预估 2–3h，用现有 35+70+21 项测试做回归保护 |

**我的建议**：若你希望"今天就能给评审一个可用的在线链接"→ 走 **A**；
若你坚持 Vercel 且愿意投入 2–3h → 走 **B**（我可以直接动手，测试会兜住回归）。
