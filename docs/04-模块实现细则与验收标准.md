> **配套文档**：`03-项目流程Spec.md`（管"什么时候做"，阶段 S0–S9）
> **本文档管**："每个模块具体做什么、拆成哪些子任务、需要哪些测试、达到什么标准才算完成"
> **不含任何实现代码**，只定义任务、测试与验收。
>
> **本版相对 `01` 的修正（第二轮复核结论）**
> 1. **新增 M0**（前置准备）：原文档把它散落在 §10，但它有明确的 DoD 与 Gate，必须成为可验收的模块。
> 2. **新增 M11**（安全/限流/配额）：方案 B 是"公网 + 服务端自备 key"，**不加防护等于把自己的额度公开**。
> 3. **新增 M12**（可观测与证据留痕）：这是"可交付性"得分的直接来源，原文档只在 M10 一笔带过。
> 4. **新增 M13**（导出与分享）：生成策略 ③ 承诺了"导出真实源码"，需独立模块承载。
> 5. **修正依赖**：LLM 适配器从 M4 拆出，前移到 M9 所在阶段（否则 M3 无法生成计划）。
> 6. **修正估时**：原 M1–M10 估时合计 620 分钟，与 8 小时预算（可用约 420 分钟）**不自洽**，本版给出分档方案（见 §2）。
> 7. **档位已定（第三轮决策）**：采用**完整档（9–10h）**，实施范围 ＝ **M0–M13 全量**。
> 8. **新增 §19 各模块功能清单**：明确每个模块"到底要实现哪些功能"，与 §3–§18 的模块章节一一对应；**模块间接口契约见 `03` §13**。

## 1. 测试与验收总纲

### 1.1 测试分层

| 标记 | 类型 | 目的 | 何时跑 |
|---|---|---|---|
| **U** | 单元测试 | 纯逻辑正确性（校验、转换、状态机分支） | 每阶段 |
| **I** | 集成测试 | 适配器与数据库、API 契约 | 每阶段 |
| **E2E** | 端到端 | 主流程贯通（含预览交互与持久化） | 每阶段末 + S9 |
| **M** | 手工走查 | 视觉、交互细节、错误文案 | 每阶段末 |
| **R** | 回归 | 用固定样例集复跑，防倒退 | 每次改动后 |

**核心原则**：**验收不是最后一步，而是每个阶段的出口**。每阶段必须预留约 10% 时间做 DoD 自检，不允许把验收压缩到项目末尾（这是原排期的隐性缺陷）。

### 1.2 固定回归样例集（三个必跑场景）

这三个需求是**固定的回归输入**，所有编排/渲染/校验的改动都必须用它们复跑：

| 编号 | 样例需求 | 覆盖能力 |
|---|---|---|
| **S-1** | "做一个个人待办清单：能新增任务、标记完成、按状态筛选、删除。" | 表单 + 列表 + 增删改 + 筛选（最小 CRUD） |
| **S-2** | "做一个活动报名与审批系统：学生提交报名，管理员审批通过或驳回，能看到自己的报名状态。" | 状态流转 + 多角色 + 详情页 + 校验（复杂度中等） |
| **S-3** | "做一个销售记录工具：录入每日销售额与产品，用图表展示汇总趋势。" | 数据录入 + 图表 + 聚合展示（看板类） |

**Mock 提供方必须对这三个样例具备确定性产出**，使自动化测试与无 key 演示都可复现。

### 1.3 每个模块统一的验收模板

每个模块的 DoD 都由四部分组成：**功能可用 / 测试通过 / 失败可解释 / 降级可生效**。任何一项不满足，模块不算完成。

## 2. 估时修正与分档方案（重要）

**问题**：`01` §3 的 M1–M10 估时合计 **620 分钟（约 10.3h）**，而 §5 排期表给模块的可用时间只有 **420 分钟**（480 减 60 buffer）。两者不自洽，会导致"按排期执行但必然超时"。

**修正后的单模块估时（精简版）**

| 模块 | 原估时 | 修正估时 | 说明 |
|---|---|---|---|
| M0 前置准备 | —（散落） | 40 | 新增，含部署空壳与 Provider 验证 |
| M1 身份与项目 | 40 | 40 | 保持 |
| M2 输入与会话 | 30 | 25 | 精简附件上传至 P2 |
| M3 计划与契约 | 30 | 30 | 保持 |
| M4 编排引擎 | 90 | 70 | 拆出 LLM 适配器后下降 |
| M5 Spec 与渲染 | 120 | 105 | 技术心脏，不压缩 |
| M6 预览沙箱 | 60 | 40 | 仅做 iframe + 错误回传 |
| M7 迭代与版本 | 60 | 35 | P1 精简：不做 diff 视图 |
| M8 校验与自愈 | 60 | 30 | P1 精简：自愈上限 2 轮 |
| M9 持久化与存储适配器 | 60 | 45 | 含 LLM 适配器 |
| M10 交付 | 70 | 55 | 含文档与复测 |
| M11 安全与配额 | — | 20 | 新增 |
| M12 可观测与留痕 | — | 15 | 新增 |
| M13 导出与分享 | — | 30 | 新增 |

**分档结论**

| 档位 | 包含 | 合计 | 是否满足"至少一个延展能力" | 差异化亮点 | 状态 |
|---|---|---|---|---|---|
| 保底 | M0–M6 + M9 + M10 + M11 + M12 | 约 **485 min（8.1h）** | ❌ **不满足** | ❌ 无 | 已排除（不合规） |
| 推荐（8h 档） | 保底 + **M7**（迭代+版本） | 约 **520 min（8.7h）** | ✅ 满足 | ⚠️ 弱（无校验自愈） | 备选 |
| **✅ 完整（9–10h 档）** | 推荐 + **M8** + **M13** | 约 **580 min（9.7h）** | ✅✅ | ✅ 强（对冲 Atoms 短板） | **已选定（第三轮决策）** |

> **✅ 已决策：采用完整档** —— M8 校验自愈与 M13 导出**进入实施范围**。
>
> 由此确定的四件事：
> 1. **实施范围 ＝ M0–M13 全量**，不再有"是否启动 M8/M13"的悬念。
> 2. **降档预案仍然保留**：若实际时间不足，按 **① 先砍 M8 → ② 再砍 M13** 的顺序逐级降档（`01` §8.1）。这条预案要写进说明文档，本身就是"复杂度控制与取舍"的展示点。
> 3. **M11/M12 在任何档位都不砍**——它们分别是"不烧光自己的额度"和"证明真的做完了"的底线。
> 4. ⚠️ **合计数字已修正（第四轮复核）**：上表原为 440/475/535 min，系**漏算 M0、M11、M12 的算术错误**，正确值为 **485/520/580 min**。
>    且以上是**纯开发工作量**；计入每阶段集成与 DoD 验收开销（约 10%）后，完整档实际约 **665 min ≈ 11.1h**（见 `03` §9 阶段合计）。
>    → **结论："9–10h" 属乐观估计**。若实际时间只有 10h，应在 S6/S7 之后启动降档预案。

## 3. M0 · 前置准备与环境打通 🅿️ P0 · 40min · 阶段 S0

**目标**：在第一小时把所有"环境类不可逆风险"清零。

**范围边界**
- ✅ 做：账号与凭据就绪、仓库建立、**公网空壳部署打通**、Provider 连通性与结构化输出验证、范围冻结
- ❌ 不做：任何业务功能

| 编号 | 子任务 | 具体动作 | 产出物 |
|---|---|---|---|
| T-M0-1 | 仓库建立 | 建 public 仓库，先写入 `.gitignore`（含 `.env*`），再谈任何密钥 | 仓库 + 首个提交 |
| T-M0-2 | 空壳部署 | 建最小可运行页面 → 用 Git 直连部署 → **拿到公网链接** | 公网链接（可打开） |
| T-M0-3 | 环境变量 | 在平台配置全部变量名（值后续填），本地建 `.env.local` | 变量清单就绪 |
| T-M0-4 | Provider 验证 | 用 DeepSeek key 真实调用一次，验证：连通性、**结构化输出稳定性**、超时表现、token 用量 | 一次合法结构化输出 + 耗时/用量记录 |
| T-M0-5 | 范围冻结 | 确认 P0/P1/P2 与"不做"清单、确认档位（保底/推荐/完整） | 冻结清单 |
| T-M0-6 | 密钥安全 | 开启 Secret Scanning，确认仓库内无任何密钥 | 检查记录 |

**测试清单**

| 编号 | 类型 | 场景 | 预期 |
|---|---|---|---|
| TST-M0-1 | M | 陌生人打开公网链接 | 3 秒内出现可用界面，无报错 |
| TST-M0-2 | I | 用真实 key 调一次结构化输出 | 返回可解析结果；失败时有明确错误 |
| TST-M0-3 | M | 全仓搜索密钥特征串 | 零命中 |
| TST-M0-4 | M | 断开网络后访问链接 | 页面仍能加载（静态部分），失败提示友好 |

**验收标准（DoD）**
- [ ] 公网链接可被非本机设备打开
- [ ] DeepSeek 成功返回**一次**符合约定结构的输出，且记录了耗时与 token 用量
- [ ] 仓库内 `git log` 与文件树中**不存在任何密钥**
- [ ] 范围与档位书面冻结
- [ ] 本地开发环境可启动（记录命令与版本）

**失败模式与降级**：Provider 不通 → 用 Mock 推进 S1，但**必须记录并持续排查**，不得静默跳过。
**风险**：账号注册/网络问题吃掉时间（触发 R7）→ 备用部署路径提前选定。

## 4. M1 · 身份与项目空间 🅿️ P0 · 40min · 阶段 S1

**测试清单**

| 编号 | 类型 | 场景 | 预期 |
|---|---|---|---|
| TST-M1-1 | U | 密码哈希与校验 | 明文不落库 |

- [ ] 项目可新建/重命名/删除；删除后不可通过 URL 访问
- [ ] 跨用户访问被明确拒绝
- [ ] 空状态有明确引导，不是空白页

**降级**：托管 DB 不可用 → 切本地 SQLite（开发）或临时 IndexedDB 适配器。
**风险**：身份做重会吃掉 1 小时 → **只做最小可用**。

## 7. M4 · 多智能体编排引擎 🅿️ P0 · 70min · 阶段 S3 ★核心

**目标**：真正的多角色协作（状态机），而非"套一层循环的 LLM 调用"。

| 编号 | 子任务 | 具体动作 | 产出物 |
|---|---|---|---|
| T-M4-1 | Run 状态机 | 定义状态与迁移；非法迁移显式拒绝（409） | 状态机 |
| T-M4-2 | 步骤调度 | 前端驱动的"短步骤"设计，**每请求一步**，规避 Serverless 超时 | 调度器 |
| T-M4-3 | 角色契约 | 5 个角色各自的输入/输出结构定义与校验 | 契约定义 |
| T-M4-4 | 事件广播 | 通过 SSE 推送 §6 事件表；`eventId` 单调递增 | 事件流 |
| T-M4-5 | 断线续传 | 支持 `Last-Event-ID`；事件丢失可用 Run 快照对齐 | 续传能力 |
| T-M4-6 | 重试与超时 | 每步超时 + 重试上限 2 次；重试耗尽进入降级 | 重试策略 |
| T-M4-7 | 调用预算 | 单 Run 调用次数上限；超限中止并如实报错 | 预算熔断 |
| T-M4-8 | 取消 | 任意步骤可取消，已产出 Artifact 保留 | 取消链路 |

**测试清单**

| 编号 | 类型 | 场景 | 预期 |
|---|---|---|---|
| TST-M4-1 | U | 状态机非法迁移 | 被拒绝，状态不变 |
| TST-M4-2 | I | 模拟某角色返回不合法结构 | 触发重试，最终降级并如实上报 |
| TST-M4-3 | I | 单 Run 超过调用预算 | 中止并给出明确原因 |
| TST-M4-4 | E2E | S-1 样例完整跑通 | 至少 3 个角色依次产出，事件顺序正确 |
| TST-M4-5 | E2E | 生成中断开事件流再重连 | 状态不丢失，无重复消费异常 |
| TST-M4-6 | M | 观察 Agent 时间线 | **不存在"永远转圈"的卡片**；每个 started 都有 finished/failed |

**验收标准（DoD）**
- [ ] 至少 3 个角色可见，各自状态与耗时正确
- [ ] 任一步失败可重试且状态一致
- [ ] 事件协议符合 `03` §6，含 `eventId` 与续传
- [ ] 调用预算与超时生效
- [ ] 前端驱动拆步，**单请求不触发平台超时**

**降级**：SSE 不可用 → 轮询 Run 快照（功能等价）。
**风险**：上下文爆炸、产物结构漂移 → 用严格 schema 校验 + 裁剪上下文。

## 8. M5 · 应用规格（App Spec）与渲染运行时 🅿️ P0 · 105min · 阶段 S4 ★★技术心脏

**目标**：把"应用"变成可生成、可校验、可增量修改的结构化规格，并确定性渲染成真应用。

| 编号 | 子任务 | 具体动作 | 产出物 |
